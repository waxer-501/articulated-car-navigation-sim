# STM32F103C6 ST Link 连接对照说明

日期：2026 年 11 月 18 日。用途：供另一台电脑连接同一块最小系统板时，对照接线、驱动、工具和参数。对象是独立铰接小车的 IMU 采集板，不是 DM MC02 或钻孔小车控制板。

我们已在 Ubuntu 电脑上通过 ST-Link/V2，以 SWD、100 kHz、Hot Plug 热连接成功读到 STM32 的标识和 32 KB Flash 容量。后续两次复核均返回运行状态。整个连接检查没有请求暂停、复位、擦除、烧录或修改保护位。

这只证明 PC → ST-Link → STM32 的调试读取链路可用，不证明当前 IMU 采集、无线回传或应用固件正常。同事电脑的操作系统、软件版本和完整报错尚未提供，下文的 Windows 项仅为对照项，不代表已在其电脑验证。

## 一 本机成功连接的基线

| 对照项目 | 我们实际使用或读取的结果 |

| 用户报告的目标板 | STM32F103C6T6A 最小系统板；不能误选 F103C8 或 H7 |
| 调试器 USB 标识 | 0483:3748，ST-LINK/V2 |
| 这支调试器的序列号 | 33FF72064243323456261357 |
| 调试器固件版本 | 2026-11-04 记录为 V2J45S7；11 月 18 日未重新查询版本 |
| 调试接口与速率 | SWD，100 kHz；工具参数 freq=100，单位是 kHz |
| 连接模式 | CONNECT_HOT_PLUG；不使用连接时复位或主动 halt |

0x0412 与 32 KB 容量同用户报告的 C6 规格一致，但不能据此识别芯片完整封装、温度等级或型号后缀。历史工具报告 SRAM 为 10240 字节、Flash 页为 1024 字节；本轮未做内存容量测试。

## 二 接线和供电对照

按板上丝印和调试器引脚定义核对，不按杜邦线颜色、照片左右或不同克隆板的排针顺序判断。

| ST-Link 信号 | STM32 最小板信号 | 核对要点 |
|---|---|---|
| SWDIO | PA13 / SWDIO | 不是 UART TX 或 RX |
| SWCLK | PA14 / SWCLK | 不是 PA13，不与 SWDIO 互换 |
| GND | G / GND | 调试器与目标板必须共地 |
| NRST | 本基准不依赖此线 | 既有烧录记录提示 NRST 未连接；本轮未目视复核接线 |
| 供电或 VTref | 按调试器具体型号核实 | 不将克隆板 3.3V 输出直接当作 VTref 输入 |

本项目此前采用最小板 USB 与 ST-Link 分别接电脑的方式。对照方案是最小板自身供电、ST-Link 接 SWDIO/SWCLK/GND；若某型号调试器需要 VTref，按其说明接目标参考电压。11 月 18 日没有重新逐线目视或测量供电接法，不能把工具电压读数当作供电接线已核验。

目标已由 USB 供电时，不额外把 ST-Link 的 3.3V/5V 电源输出与板上电源并联。BOOT0 正常运行应为 0；本次未改跳帽，也未目视确认当前跳帽状态。改线先断电，检查排针焊接与接触，杜邦线不宜松插裸焊孔。

## 三 Ubuntu 上准备工具和 USB 权限

以下命令从仓库的 hardware 目录执行。安装只恢复本项目的依赖；权限脚本只配置主机 USB 访问，不会连接、复位或烧录 MCU。本节没有要求同事先运行任何烧录命令。

仓库：https://github.com/waxer-501/articulated-car-navigation-sim

```bash
cd /实际路径/articulated-car-navigation-sim/hardware
bash 安装实机环境.sh --with-firmware-tools
```

此安装入口已验证的环境为 Ubuntu 22.04 x86_64，不能原样用于 Windows。若 cc 不存在，需要先由电脑管理员准备 C 编译环境。已有工具不必重复安装。

先看电脑是否识别调试器：

```bash
lsusb -d 0483:3748
id -nG
```

本轮 USB 节点为 /dev/bus/usb/001/011，权限为 crw-rw----，属主 root、组 plugdev；本机用户 gyt 已在 plugdev 组。Bus 和 Device 编号会变化，同事应使用自己的 lsusb 输出，不能照抄 001/011。

Linux 提示 Permission denied、LIBUSB_ERROR_ACCESS 等访问错误时，再安装项目规则：

```bash
sudo bash tools/enable_stlink_access.sh
```

规则文件为 /etc/udev/rules.d/60-sweeper-stlink.rules，内容如下：

```text
SUBSYSTEM=="usb", ENV{DEVTYPE}=="usb_device", \
ATTR{idVendor}=="0483", ATTR{idProduct}=="3748", \
GROUP="plugdev", MODE="0660", TAG+="uaccess"
```

上面换行仅为排版，实际文件是一行。脚本会原样安装仓库中的规则、重载规则并触发对应设备；存在不同旧规则时会备份。不要用 sudo 执行整套烧录程序来掩盖权限问题。若规则安装后仍无访问权，检查用户组与桌面会话授权；需要加入组时由管理员处理并重新登录。

Windows 电脑没有 udev，不执行这一权限脚本。请对照设备管理器中是否正确识别 ST-Link、ST-Link USB 驱动、所用软件版本和调试器序列号。ST-Link 调试连接不使用 COM 口；CH340 无线接收串口与此连接是两条链路。

## 四 我们使用的连接命令

### 标准工具的历史成功命令

2026-11-04 使用下列命令成功读取芯片信息；2026-11-18 使用下一小节的自定义只读探针。这里保留日期，避免把历史工具版本误写成今天刚重新读取。

```bash
LD_LIBRARY_PATH="$PWD/.toolchain/usr/lib/x86_64-linux-gnu" \
  .toolchain/usr/bin/st-info --probe --hot-plug --freq=100
```

该历史输出为：

```text
Found 1 stlink programmers
  version:    V2J45S7
  serial:     33FF72064243323456261357
  flash:      32768 (pagesize: 1024)
  sram:       10240
  chipid:     0x0412
  descr:      F1 Low-density device
```

不要把旧版工具不识别 --hot-plug / --freq 的参数错误当作目标损坏；先对照工具版本。项目局部 st-info --version 已在本轮文档整理时核对为 v1.7.0。此命令的 --probe 用于枚举，不在命令中写死某支 ST-Link 的序列号。

### 本轮使用的自定义只读探针

源文件为 tools/stlink_target_probe.c。它使用 stlink_open_usb(UERROR, CONNECT_HOT_PLUG, serial, 100)，读取目标标识、状态和少量地址后释放调试连接；没有调用 halt、reset、run、erase、目标写入或 Flash 编程 API。

```bash
mkdir -p build/host
cc -std=c11 -Wall -Wextra -Werror \
  -I.toolchain/usr/include/stlink \
  -I.toolchain/usr/include/libusb-1.0 \
  tools/stlink_target_probe.c \
  -L.toolchain/usr/lib/x86_64-linux-gnu \
  '-Wl,-rpath,$ORIGIN/../../.toolchain/usr/lib/x86_64-linux-gnu' \
  -lstlink -o build/host/stlink_target_probe
./build/host/stlink_target_probe
```

重要：这个自定义源文件写死了序列号 33FF72064243323456261357。如果同事用的是同型号的另一支 ST-Link，必须先取得那支设备的实际序列号并调整选取值，或先用标准枚举命令检查。若真的是同一支实物调试器，不应因换电脑而换序列号。Linux 的 lsusb -v 有时显示原始序列号控制字符，不能直接把那串乱码当作工具使用的十六进制序列号。

不要让 IDE、CubeProgrammer、OpenOCD、st-util、另一窗口的监视器同时占用同一支调试器。结束其他调试会话后只运行一个连接工具。

本轮先执行一次探针，发现首次状态为 3 后，因该状态仍需核实，间隔约 0.5 秒做了两次相同只读复核。这不是自动复位重试，也没有重新上电。正常标识读取通常几秒内完成；Ctrl+C 只结束主机读取，不能保证停止 MCU。此通用探针会读取现有程序状态，不验证应用行为。

## 五 今天实际读到的结果

首次输出关键行：

```text
chip_id=0x00000412 flash_bytes=32768
core_id=0x1ba01477 voltage_tool_mV=3226
status_rc=0 core_state=3
addr=0xe0042000 rc=0 value=0x10006412
addr=0xe000ed00 rc=0 value=0x411fc231
addr=0x08000000 rc=0 value=0x20002800
```

两次复核均为 status_rc=0、core_state=1，电压读数分别为 3226 和 3233 mV。libstlink 1.7.0 的枚举中，1=TARGET_RUNNING、2=TARGET_HALTED、3=TARGET_RESET；这些整数不是所有软件通用的错误码。

据此可确认：同一支调试器能识别目标，并读回符合 F103C6 规格的 Flash 容量和 Cortex-M3 标识，复核时工具报告 CPU 运行。首次 RESET 状态及 DHCSR 中复位状态位的原因未进一步确认，不能仅凭该单条记录断定芯片持续复位，也不能宣称已经证明完全没有重启。

本轮探针还记录到 SRAM 0x20000000 为 0xb2b6d2b9，与旧采集固件预期的诊断标记 0x31444d49 不一致。本轮没有进一步验证现有固件或采集状态。f103_swd.py capture 和监视器有诊断格式要求，它们不识别数据时，不能直接推导为 SWD 连接失败，也不应因此直接重刷程序。

连接通过的标准是目标身份和读取结果符合预期，不只是“看到 ST-Link”或探针进程返回 0。芯片 ID 为 0、Flash 为 0、读取返回错误，或不同地址反复出现同一异常值，都不能当作目标读取通过。

## 六 按失败层级进行对照

| 同事端现象 | 优先核对 | 与本机结果的区别 |
|---|---|---|
| 电脑看不到 ST-Link | USB 线、插口、集线器、驱动、调试器本身 | 本机能枚举 0483:3748 |
| 能枚举但无法打开 USB | Linux 权限、用户组，或 Windows 驱动；是否被其他程序占用 | 本机非 root 用户有访问权 |
| No ST-Link found | 是否选错序列号；是否只是同型号的另一支调试器 | 自定义探针固定选择本机序列号 |
| 能打开调试器但芯片 ID 为 0 | 目标供电、共地、SWDIO/SWCLK、接触、模式与 SWD 时钟 | 本机读到 0x0412 与 32768 字节 |
| 默认参数失败，低速连接成功 | 是否使用 SWD、100 kHz、Hot Plug | 不直接沿用工具默认 MHz 时钟 |
| 只有连接时复位模式可连 | 现有程序、SWD 引脚使用、NRST 连接和复位模式 | 这是另一种诊断条件，不能写成本机热连接基线 |
| 监视器提示固件不匹配 | 诊断 ABI、当前 Flash 内容；先用通用探针分层判断 | 连接成功不等于旧 IMU 诊断区有效 |

若前述只读方法仍失败，保留原始错误输出再讨论下一步。不要先擦除芯片、关闭读保护、更新 ST-Link 固件或切换会复位目标的连接方式；这些操作会改变当前证据或设备状态，需要另行明确范围。
