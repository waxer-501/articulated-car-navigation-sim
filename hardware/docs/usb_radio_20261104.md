# TX → RX USB 无线台架记录（2026-11-04）

## 角色与范围

用户确认两块 USB 底板分别只用于 TX 发射、RX 接收。本次所有程序只向 TX 写测试数据，只从 RX 取回数据；没有反向应用消息、传感器配置命令或车辆控制指令。

| 角色 | 已确认 USB 拓扑 | 当前串口 | 稳定路径 |
|---|---|---|---|
| RX | `1-1.2` | `/dev/ttyUSB0` | `/dev/serial/by-path/pci-0000:00:14.0-usb-0:1.2:1.0-port0` |
| TX | `1-1.4` | `/dev/ttyUSB1` | `/dev/serial/by-path/pci-0000:00:14.0-usb-0:1.4:1.0-port0` |

两端 USB 都枚举为 `1a86:7523` CH340，没有独立序列号。身份通过用户暂时拔下 TX、保留 RX 后确认。不能用相同的 `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0` 区分这两块板。表中的拓扑只适用于本开发电脑及当前插口，移到树莓派后须重新枚举。

## 串口修复

内核日志显示 CH341 曾创建串口，随后 BRLTTY 设置 USB 配置并使串口断开。用户执行了已审查的 `tools/fix_radio_usb.py --apply`：

- 备份目录 `/var/backups/sweeper-radio-20261104-164147`。
- 仅对上述两个插口上的 CH340 跳过 BRLTTY 误识别；没有卸载或全局禁用 BRLTTY。
- 重新绑定 `ch341`，为当前桌面用户授予两端串口访问权限。
- 此修复没有打开串口发送数据。

恢复原规则的入口：

```bash
sudo /usr/bin/python3 tools/fix_radio_usb.py --restore /var/backups/sweeper-radio-20261104-164147
```

## 模式与厂家证据

原始厂家包：`http://www.ashining.com.cn/data/as01_ml01d.zip`，SHA-256 `cc0ddf53418bc004351c4af4a4eef3cd2e47cdce4ebae2f9f48fa6497f8e110e`。

包内开发板手册 `vendor/radio/as06_vtb01_manual.pdf` 第 2 页说明：TX 上电默认固定发送 `ashining`；长按模式切换按钮、绿灯闪 3 次后进入串口发送模式；UART 为 9600、8N1，每次用户数据不超过 16 字节。该文件名写 VTB01，页眉写 VTB07；不能据文件名推定实物底板的准确版本。

实测先收到 `ashining`，自定义标记未通过；用户按上述方式切换后，自定义标记通过。当前已验证的是行为和串口设置，未读取实物射频寄存器。

资料中的 STM8L101 示例使用信道 60、250 kbps、地址 `34 43 10 10 01`、动态载荷、1 字节硬件 CRC 和 pipe0 自动应答。这些保存在配置的 `reference_air_parameters` 中，**仅作为后续 MC02 驱动的源码依据，不是实物寄存器读回结果**。芯片内部自动应答与应用数据 TX→RX 分工应分别记录。

## 实测结果

| 检查 | 结果 | 证据文件（本机 captures 目录） |
|---|---|---|
| 上电固定模式 | RX 连续收到 ashining，自定义标记 0/3 | `link_9600.json` |
| 切到串口模式 | 自定义 ASCII 标记 3/3，逐字节相等 | `link_9600_serial_mode.json` |
| 小包边界与内容 | 8、15、16 字节 ASCII；8、16 字节二进制均原样通过 | `content_and_size_probe.json` |
| 32 字节包拆 16+16，片间隔 50 ms | 20 包中 0 包收到；失败保留 | `synthetic_telemetry_roundtrip.json` |
| 相同数据，片间隔改为 300 ms | 20/20 包、640/640 字节相等，顺序正确，CRC 错误 0 | `synthetic_telemetry_roundtrip_300ms.json` |

所有证据位于 `captures/usb_radio_20261104/`。遥测包均为程序构造的测试值，**不是实际 IMU 测量**。没有连接 MC02 或 IMU 进行这次台架实验。

厂家示例使用串口轮询超时来分包，接收循环有 100 ms 等待并清空 FIFO。这支持“过密输入可能被合并或丢弃”的解释；尚未确认实物固件是否逐行等同于示例，不能据此声称根因已由源码完全证明。已实测的结论是：50 ms 失败、300 ms 通过，尚未扫描最高可靠速率。

## 频率限制

9600、8N1 的理论串口有效载荷上限为 960 字节/秒，尚未扣除底板等待和处理时间。当前格式每只 IMU 每帧 32 字节：

- 两只各 100 Hz 需要 6400 字节/秒，超过该 UART 上限。
- 两只各 25 Hz 需要 1600 字节/秒，也超过该 UART 上限。
- 300 ms 分段间隔本次只证明低速可用，不是目标采集频率或最大性能。

正式高频链路优先评估 MC02 SPI 发射、树莓派直接 SPI 接收；保留 USB 底板时必须接受较低更新率或另行修改已确认型号的底板固件。没有进行底板刷写或树莓派系统修改。

## 可复现入口

这些命令只用于当前两块独立 USB 无线板，发送端需先进入串口模式。接收端从不由程序发送数据。

```bash
# 约 7 秒以内，3 条短标记；不发送任何配置命令
.venv/bin/python tools/check_usb_radio_link.py --baud 9600 --output captures/new_ascii_check.json

# 约 14 秒，20 个合成遥测包；每个 16 字节片段间隔 300 ms
.venv/bin/python -m tools.check_usb_radio_telemetry --fragment-interval 0.3 --output captures/new_binary_check.json

# 仅接收 v1 遥测字节流，明确指定 RX 和已验证波特率
.venv/bin/python -m sweeper_hw.usb_receiver --port /dev/serial/by-path/pci-0000:00:14.0-usb-0:1.2:1.0-port0 --baud 9600 --seconds 30 --output captures/rx_only.jsonl
```

`Ctrl+C` 停止主机程序继续写入或读取；并不保证底板停止其内部固定发射任务。拔下 TX 的 USB 电源可直接断开发射端。重新上电后应重新核对发送模式。
